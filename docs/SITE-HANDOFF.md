## Тёмная тема: как перевести следующую страницу

Читает вторая модель. Перевод страницы = атрибут + уборка её локальных
хардкодов, без нового CSS (если пришлось писать новый CSS под тёмную —
значит, хардкод не найден, ищи ещё).

1. **Атрибут.** `<html lang="ru" data-theme="dark">` в самой странице (статика)
   или добавить `theme: "dark"` в её запись `ROUTE_MANIFEST` (V3/прочее — тогда
   атрибут проставит `scripts/prerender.ts`, функция `applyTheme`, сама).
   Плюс `<meta name="theme-color" content="#0A0A0A">` в `<head>` (для V3-страниц
   тоже `applyTheme`, руками не дублировать).
2. **Найди локальные хардкоды.** Обычно это: (а) свой `:root`/`#id`-блок,
   заново объявляющий `--red`/`--black`/`--white`/`--site-bg`/`--site-text`
   и подобные легаси-имена под тёмный вид одной страницы — удалить целиком;
   (б) буквальные hex/rgb в инлайн `<style>` — искать `#[0-9a-f]{3,6}` и
   `rgba(0,0,0` / `rgba(255,255,255` с НЕ-декоративной ролью (текст, заливка,
   граница контрола — не тонкий разделитель) — заменить на `var(--ds-*)`.
   Ролевая таблица (значения — в design-system.css `:root[data-theme="dark"]`):
   фон → `--ds-bg`, поверхность/карточка → `--ds-surface`, текст → `--ds-text`,
   вторичный текст → `--ds-text-secondary`, акцент → `--ds-orange`, подпись на
   заливке акцента → `--ds-on-accent`, декоративный разделитель →
   `--ds-border`, граница контрола → `--ds-border-strong`.
3. **Скругления.** Только у стекла (`backdrop-filter: blur`). Всё остальное —
   `border-radius: 0` (брутализм, §3 промпта). На пилоте это тоже нашлось и
   поправлено — не только цвет.
4. **Шапка/подвал сами не перекрашиваются и не обязаны.** Проверено на живой
   светлой странице: подвал `.site-static-footer-shell` уже `#080808`/PAPER
   на ВСЕХ статических страницах, шапка `.site-static-header` уже светлая
   пилюля на всех — это фиксированный хром независимо от темы тела страницы,
   тот же паттерн, что у V3. Не чинить, если только не найдётся страница, где
   это внезапно не так.
5. **Тесты.** Добавить файл страницы в `SCANNED_FILES` `tests/palette.test.ts`
   (литералы hex вне брендбука); если встретилась НОВАЯ комбинация
   цвет-на-фоне — добавить пару в `scripts/contrast.ts` `PAIRS` с ролью
   (`text`→4.5 или `large-ui`→3.0) и её реальным контрастом (запусти
   `npx tsx -e "import {contrastRatio,BRAND} from './scripts/contrast.ts'; console.log(contrastRatio(BRAND.X,BRAND.Y))"`,
   не изобретай число). `tests/theme.test.ts` подхватит страницу из
   `ROUTE_MANIFEST` сам.
6. **Проверка — через инструмент, не на глаз (PROMPT-31 §4.4).**
   `npm run build`, затем `npx tsx scripts/computed-style-audit.ts --only
   /твоя-страница` (нужен `npx playwright install chromium`, если браузера ещё
   нет) — снимает фон/текст/кнопку/шапку/подвал на 1440 и 390, состояния
   hover/focus-visible, контраст и горизонтальное переполнение, пишет отчёт в
   `docs/audit/computed-style.auto.md`. Без `--only` — прогон по всем 70

`scripts/staticShellTemplate.ts` их не дублирует).

**Три ловушки, которые нашлись только живой проверкой (getComputedStyle на
деплое) — следующая страница на `bb-*` в них тоже попадёт, если не знать:**

1) **Имена классов пересекаются с `public/site-skin.css`.** У него есть и
   безусловные (не `.site-static`-scoped) правила `!important` на общие имена
   вроде `.tag`, `.platform`, `.price-card`, `.price-desc`, `.faq-a`,
   `.price-label`, `.foot-copy` — тёмный текст/светлый фон, рассчитанные на
   старые Inter-страницы, — и правила, навешиваемые после гидратации через
   `body.site-static`/`.site-static :is(...)` (например
   `.site-static :is(.grid-3, .price-row, .price-grid) { grid-template-columns:
   repeat(12,...) !important }`, ломает произвольную сетку). Обе категории
   бьют по совпадению ИМЕНИ класса, а не по смыслу. Новый локальный класс на
   странице с `bb-*` — сверяй с `grep -n "\.имя\b" public/site-skin.css`
   прежде чем использовать; если пересекается — свой префикс (на пилоте —
   `mk-`), а не борьба со специфичностью.
2) **`<header>`/`<footer>` без атрибутов на статических страницах не
   принадлежат странице целиком.** `public/site-shell.js` навешивает класс
   `site-static-header`/`site-static-footer-shell` на ЛЮБОЙ `<header>`/`<footer>`
   в рантайме и не трогает содержимое, только класс — а `site-skin.css`
   красит `.site-static-header` светлой PAPER-пилюлей безусловно, `!important`
   (это и есть «фиксированный хром независимо от темы» из раздела «Тёмная
   тема» выше). Вложенный `bb-nav` со своей полупрозрачной стеклянной заливкой
   поверх этой пилюли даёт грязно-серую полосу — стекла там и не должно быть
   (правило 11: «стекло — только где за ним глубина», а за светлой пилюлью
   глубины нет). Рабочий приём с пилота: `#page-marketplace header.site-static-header
   { padding: 0 !important }` + сплошной непрозрачный `background: var(--ds-bg)`
   у `bb-nav` внутри — не глушить слой сайтвайд, а перекрыть его площадью
   своего компонента на этой одной странице. Подвал трогать не нужно —
   `.site-static-footer-shell` уже `#080808`/PAPER, тёмная и так.
3) **`section { color: #111 !important }` + `.site-static a { color: inherit }`
   (специфичность 0,1,1 — выше любого одиночного класса без своего тега).**
   Любая `<a>` внутри `<section>` без явного цвета ПРЯМО на себе (а не
   унаследованного) наследует принудительный `#111` — тёмный текст на тёмном
   у вторичных кнопок/тегов, даже если у класса самого по себе есть
   `color: var(--ds-*)` — специфичность `.site-static a` выше голого класса.
   Фикс на пилоте — один раз у корня: `#page-marketplace section { color:
   var(--ds-text) !important }` (специфичность через `#id` перебивает голый
   `section`). Точечно унаследованный цвет у `.mk-tag` из-за этого стал чуть
   ярче задуманного (PAPER вместо FOG) — не баг, а сознательно принятый
   компромисс ради читаемости, без гонки специфичностей на каждый класс.

Ни один из этих трёх слоёв (`site-skin.css`, `site-shell.js`) в этой задаче
не снимался и не менялся — только точечные, с `#page-marketplace`-scope,
переопределения на одной странице, как и просил PROMPT-30 §8.3.

## Ловушки этого проекта

Это главное, что модель обязана знать до первой правки. Всё перечисленное
уже стреляло, и не по одному разу.

**1) Маршрута нет в пре-рендере — страницы для поиска не существует.**
Сборка зелёная, тесты зелёные, в браузере страница открывается — а робот видит
пустой `<div id="root">`. Так `/ceny` месяц отдавал поисковику семь цен из
семнадцати. Любая правка, добавляющая или переносящая страницу, обязана
пройти через пре-рендер и H1-гейт.

**2) Роутинг ручной.** Компонент `V3App` читает `window.location.pathname`,
router-библиотеки нет. Привычные паттерны React Router здесь просто не работают.

**3) Шесть систем шапки и подвала.** Источник данных теперь один
(`navigation.data.ts`, фаза 4) — но вёрстка всё ещё в шести разных местах,
правка стиля «в шапке» по-прежнему может не доехать до всех систем, если
трогать не токены/данные, а разметку конкретной системы напрямую.
Таблица систем — в «Состояние сайта».

**4) Объявленное не доходит до рендера.** Слои `!important` в `site-skin.css`,
потерянная специфичность, забытая подключённая таблица стилей. Проверять надо
**вычисленный стиль** (`getComputedStyle`), а не исходник. Скриншоты в этом
проекте врали многократно — на них полагаться нельзя.

**5) Второй источник истины.** Захардкоженные цены в разметке, захардкоженные
счётчики в тестах и заголовках, `nth-child` вместо смысловых селекторов,
генерируемые файлы в git. Любая правка, которая заводит второй источник
для одного и того же факта, — брак, даже если внешне работает. Свежие примеры:
`portfolio.data.ts` (мёртвый реестр, валидатор проверял его вместо живого) и
`src/config/routes.ts` (мёртвый параллельный список маршрутов) — оба найдены
и удалены в этом заходе.

**6) `git mv` и `git rm --cached` автоматически стейджат.** Отсюда случайно
склеенные коммиты. Перед каждым коммитом — `git status` глазами.

**7) «Сборка зелёная» не значит «CSS разобран».** Правка `.v31-*` в
`design-system.css` (`912b860`) обрезала правило от последней строки
многострочного селектора и оставила висячие списки: `vite build` прошёл,
тесты прошли, а esbuild начал писать `Unexpected "@keyframes"` — часть файла
перестала разбираться. Признак был ровно в выводе сборки, и только там.
После любой резки CSS: смотреть stderr esbuild и число правил до/после, а не
только код возврата.

**8) `waitUntil: "load"` — это середина анимации, а не состояние страницы.**
`getComputedStyle` сразу после `load` отдаёт стартовое значение перехода: на
`/content-day` в этот момент играёт 33 анимации, и ссылка шапки читалась как
`rgba(10,10,10,.72)` вместо победителя каскада `--site-muted`. Два прогона
одного кода расходились, и это выглядело как регрессия правки, которой не
было. Перед любым замером стилей надо ждать покоя конечных анимаций
(бесконечные и scroll-driven не ждать — они не заканчиваются), а `:hover`
снимать после `page.hover()`, не перекладывая курсор на следующий элемент.
Готовое ожидание — `waitForSettled()` в `scripts/computed-style-audit.ts`.
`tests/mobile-audit.test.ts` ловил тот же класс бага скрыто: у него была
своя попытка ожидания, `await (...).filter(...).map((a) => a.finished...)`
— `await` массива промисов не ждёт ничего (массив не thenable, резолвится
сразу), поэтому тест был тихо флаки: три подряд прогона одного и того же
кода давали 730/799/802 узла ниже порога. Чинится `Promise.all(...)` вокруг
`.map(...)` (PROMPT-31 §2.5) — после фикса три прогона подряд дают одно
число. Если пишешь новое ожидание анимаций руками — `Promise.all`, не голый
`.map`.

**9) Headless Chromium без `isMobile`/`hasTouch` завышает 390 на ~17px.**
`window.innerWidth` получается шире `document.documentElement.clientWidth`
на классический жёлоб под вертикальный скроллбар — которого на настоящем
телефоне (оверлейный скроллбар) нет. `position: fixed; inset: 0` элементы
(баннер cookie, `.v3-header`, `.site-static-header`) ложатся по этой
завышенной ширине и создают МНИМОЕ горизонтальное переполнение: проверено
живьём на пилоте — единственный «элемент шире вьюпорта» был сам баннер
cookie, никакого реального контента шире экрана не было. Фикс — не
`overflow-x:hidden` (он ТОЖЕ маскирует настоящее переполнение от храповика,
проверено: инъекция тестового div на 600px не ловилась с ним), а два
отдельных `browser.newContext()` в `scripts/computed-style-audit.ts` и
`tests/mobile-audit.test.ts` — десктопный (1440, без эмуляции) и мобильный
(390, `isMobile: true, hasTouch: true, deviceScaleFactor: 3`). После этого
мнимое переполнение ушло почти полностью (1294px → 21px по всем 70
маршрутам), а настоящее (`grid-template-columns: 1fr` без `minmax(0, 1fr)`
рядом с длинным словом в заголовке — минимум 4 места нашлось в
`.v3-project-card`/`.v3-project__head`/`.portfolio-posters`/`.portfolio-row`)
осталось ловиться как и должно.

### Ночная SEO-17: даты существенного изменения страницы

Sitemap больше не берёт дату общего React-каталога для всех маршрутов. При публикации сравнивается содержимое каждого canonical URL (текст, ссылки, изображения, метаданные и JSON-LD), исключая CSS-классы, навигацию, аналитику и хеши сборки. Только изменённые/новые страницы получают дату исходного release-коммита; неизменённые сохраняют подтверждённую дату. Для неизменённой страницы без истории lastmod опускается, пока содержимое не изменится. deploy.sh сохраняет content-history.json вне checkout после проверки выдачи всех публичных страниц; standalone-сборка без истории не выдумывает даты. Проверки сохранности дат, additions/deletions, смены ссылок/медиа и игнорирования layout добавлены в tests/indexnow.test.js. Ночная очередь: SEO-17 реализовано локально; production-проверка и формирование первой истории при разрешённой публикации ещё впереди.
