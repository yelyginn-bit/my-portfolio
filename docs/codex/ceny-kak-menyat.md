# Как менять концепцию цен

Проверено по коду20.10.2026. Эта инструкция ничего не меняет в значениях цен. Новая схема и её суммы сначала должны быть подтверждены владельцем. Не восстанавливать старые суммы из main или исторических документов поверх принятого PROMPT-40.

## Источники и зависимости

| Файл | Что определяет | Что проверить при новой схеме |
|---|---|---|
| `src/lib/pricing.data.ts`: `PUBLIC_PRICES`, `PUBLIC_PRICE_BY_ID` | Публичные предложения: id, строка price, описание, состав, ограничения, сроки, href/portfolioHref, showOnCatalog | Не создавать вторую копию сумм в HTML; сохранить стабильность id и смысл единицы услуги |
| Там же: `ESTIMATE_DATA` | Группы калькулятора, base/options, priceMin/priceMax, unit, replaces | Не считать строку каталога готовой моделью расчёта: диапазоны, единицы и замена базы должны соответствовать новому договорённому смыслу |
| `src/lib/pricing.config.ts`, `src/lib/calc.ts`, `src/lib/discounts.ts` | Лимиты количества, срочность, скидка, формула и округление | Отдельно согласовать условия коэффициентов; проверить границы и комбинации, а не только итог одного тарифа |
| `src/prices/Prices.tsx` | Каталог `/ceny`, состав и ограничения, ссылки на работы | Карточка и подпись цены не противоречат друг другу; showOnCatalog учитывается |
| `src/config/site.ts` | SERVICE_SUMMARIES с ценами по ссылкам PUBLIC_PRICE_BY_ID | Краткие карточки услуг обновляются от источника, новая услуга связана с правильным id |
| `src/calculator/Calculator.tsx` | Выбор позиций, смета и текст заявки | Единицы, количество, замена базы, диапазон и готовое сообщение соответствуют расчёту |
| `scripts/priceGuard.ts` | Подстановка `data-price-reference`, деталей фото-статьи, контроль чисел JSON-LD | Новые id распознаются; неизвестный маркер должен по-прежнему останавливать сборку |
| `vite.config.ts` | Подстановка цен статических страниц и числовые Offer трансляций | minPrice/maxPrice/priceCurrency и единицы проверены по новой модели; не получать выдуманное число из произвольного текста |
| `scripts/aiDiscovery.ts`, `src/lib/aiDiscovery.ts` | Общая поисковая разметка, OfferCatalog и описания предложений | JSON-LD согласован с видимой ценой, составом и ссылкой услуги |
| `scripts/llms.ts` | Публичный `/llms.txt` | Цена и адрес услуги берутся из того же источника; недействующие предложения удалены по согласованной схеме |
| Статические `*.html`, статьи блога, `src/public/V3App.tsx` | Видимые блоки и ссылки на источник | Нет оставшихся старых обещаний, единиц, сроков или буквальных цен |

`PUBLIC_PRICES` и `ESTIMATE_DATA` — два представления в одном исходном файле. Они не синхронизируются автоматически путём изменения одной строки price. Если услуга меняет единицу тарификации, нужно согласованно изменить каталог и правила расчёта, а не подогнать одно число.

## Важная граница runtime/БД

`src/lib/pricing.runtime.ts` умеет хранить override, читать активные `price_rules`, преобразовывать их в EstimateData и засеивать пустую таблицу. При преобразовании свойства replaces подтягиваются из статического конфига. `src/admin/PriceRules.tsx` редактирует таблицу через getStore.

Однако текущий публичный `Calculator.tsx` задаёт `DATA = ESTIMATE_DATA` и явно передаёт DATA третьим аргументом computeBreakdown. В нём нет вызова hydratePriceRules. Значение по умолчанию getActiveEstimateData в самой функции расчёта не заменяет явно переданный аргумент. Поэтому нельзя обещать, что нажатие кнопки админки уже обновило публичный калькулятор. Комментарий или надпись админки не сильнее кода. Изменение этого поведения — отдельная задача с проверкой согласованности, авторизации и источника цен.

Production БД, сидирование, .env, admin и правила скидок этим документом не меняются. Не вызывать seedPriceRulesFromConfig ради проверки инструкции: это запись в хранилище.

## Порядок будущего изменения

1. Зафиксировать подтверждённую схему: что является услугой, единица, минимальный объём, диапазон или фиксированная цена, состав, ограничения, сроки, срочность/скидки. Не заполнять отсутствующие факты предположениями.
2. Создать отдельную ветку от актуальной принятой базы. Найти ссылки на затронутые id и типы съёмки; проверить каталог, услуги, статьи, калькулятор, сообщения заявки и JSON-LD. Не править dist вручную.
3. Изменить источник pricing.data.ts и только необходимые потребители. При новой единице расширить PriceUnit и unitLabel/формулу осознанно; при новой группе проверить service-context. Сохранить правило заменяющего тарифа replaces, если оно по-прежнему предусмотрено схемой.
4. В статическом HTML оставить ссылки-маркеры на цены. Для новой числовой schema-модели хранить проверяемые числовые поля в источнике, а не дублировать сумму в шаблоне. Российская строка «от…» сама по себе не подтверждает конкретный Offer.price или верхний предел.
5. Добавить независимые примеры расчёта по новой согласованной схеме: минимум/максимум, количества, срочность, скидка, взаимоисключающие тарифы и замена базы. Сохранить старые проверки для не затронутых услуг. Не удалять assert только потому, что он мешает новой схеме; менять ожидаемый бизнес-результат можно лишь с подтверждением и объяснением.
6. Собрать сайт и просмотреть `/ceny`, затронутые услуги и калькулятор на390/1440, в том числе весь текст состава и итог. Проверить реальный HTML и JSON-LD, а не только JSX. Цены и единицы в сообщении заявки должны совпасть с показанным расчётом; production-форму без отдельного разрешения не отправлять.
7. Выполнить полный check перед каждым коммитом, посмотреть git status, сделать понятный русский коммит, отдельный PR и зелёный основной CI. Обновить SITE-HANDOFF и log в том же проходе. При падении остановить этот пункт и записать причину в QUEUE, без ослабления тестов.
