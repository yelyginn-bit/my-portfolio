# Мёртвые правила в `src/design-system.css`

Разведка для Claude Code (QWEN-06 §В). **Ничего не удалено и не изменено** —
файл чужой, и чистить его будет тот, кто владеет. Здесь список вида «селектор,
строки, почему мёртв» и границы метода.

## Как мерилось и как повторить

```bash
npm run build
npx tsx scripts/dead-selectors.ts --css src/design-system.css
```

Инструмент делает две вещи, которые по отдельности ничего не доказывают:

1. разбирает файл стеком скобок (вложенность `@media` **и `@layer`** сохраняется,
   шаги `@keyframes` отбрасываются) и проверяет каждый селектор
   `document.querySelectorAll` на живом рендере **75 маршрутов** (70 публичных +
   4 приватных + служебные, кроме редиректов) на 1440 и 390;
2. для селекторов, не нашедших узла, ищет имя класса в исходниках, способных
   дорисовать DOM после загрузки: `*.tsx`, `*.ts`, `*.js`, `*.html` (кроме
   самого `dist/` и самого измерителя — иначе его комментарии считались бы
   потребителями).

Правило считается мёртвым только если не сработало и то и другое. Полный
вывод — `.night-shots/dead-design-system.css.tsv` (366 строк, вне git).

## Копии (100 правил, 15 семейств)

Здесь селектор мёртв в `design-system.css`, но **то же имя** оформлено правилом
в другом stylesheet'е — то есть удаление ничего не изменит в отрендеренных
стилях, а вот порядок подключения важен.

| семейство | правил | строки | где второй экземпляр |
|---|---|---|---|
| `.site-home*` | 64 | 343–1008 | `src/index.css` (93 правила того же имени) |
| `.direction-*` (hero, card, category-card, category-copy, category-grid, grid, cta, page) | 21 | 427–493 | `src/index.css` |
| `.v32-showreel*` (5), `.v32-broadcast-artifact*` (5), `.v3-broadcast*` (4), `.v32-proof__davinci` (1) | 15 | 730–1399 | `src/index.css`, `src/v3-polish.css` |
| **итого** | **100** | | |

`.site-home` — самое крупное и самое безопасное: как **класс** он не встречается
во всём репозитории нигде, кроме двух CSS-файлов (`grep -rl "site-home"` →
`src/index.css`, `src/design-system.css`, `docs/audit/dark-theme-inventory.md`).
То есть 64 правила в `design-system.css` + 93 в `index.css` = 157 правил
описывают DOM, которого не существует. Это ровно те 136 «копий», которые
QWEN-05 нашёл со стороны `index.css`; теперь видно и с этой стороны.

## Порядок, в котором это безопасно удалять

1. Сначала `src/index.css` (задача А этой смены, застопорилась на шаге ноль):
   его 324 правила корзины «класса нет нигде» не пересекаются с chrome-работой
   Claude Code вообще.
2. Затем `.site-home*` из `design-system.css` — 64 правила, ни одного
   потребителя, ни одной ссылки на них из рантайма.
3. Затем остальные 76 «мёртвых» семейств — по одному коммиту на семейство.
4. Копии (100) — только вместе с проверкой порядка подключения: сегодня
   `design-system.css` грузится **до** `index.css` на `/ceny` и
   `/cvetokorrekciya`, и удаление копии из одного файла может открыть правило из
   другого, которое сейчас перебито.

После каждого шага — `style-fingerprint` (`--label/--diff`, с 89a3aa2 он видит и
ритм текста) и `visual-diff` на всех 140 кадрах; ожидание — ноль расхождений,
кроме случаев, когда удаляемое правило всё-таки что-то красило.

## Чего этот замер не доказывает

- **Приватные страницы.** `/account`, `/admin`, `/journal`, `/portfolio/photo`
  отдают до авторизации оболочку, поэтому их `.adm-*`, `.gal-*`, `.j-*` попали
  в третью корзину («имя есть в коде»), а не в мёртвые. Проверка по исходникам
  их бережёт, но глазами за авторизацией никто не смотрел.
- **Состояния по действию.** Открытое меню, принятое куки, модалка, сравнение
  «до/после» на `/cvetokorrekciya` — тот же случай: имена живы в коде, в
  первом рендере их нет.
- **Классы, которые приходят из данных.** Если имя когда-нибудь приедет из
  Supabase (например, в `className` проекта), замер его не предвидит.
- **`main` уже другой.** Chrome переписывается прямо сейчас (PROMPT-33), и
  конфликт `site-skin.css` в шаге ноль это видно. Перед удалением список стоит
  прогнать ещё раз на слитой ветке: команда одна и та же, 4 минуты.
