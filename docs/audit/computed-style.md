## 1. Ответ на вопрос (а): локальный `:root` статических страниц до рендера НЕ доходит

Замерено на `/reels` и `/photo` (две независимые страницы); структура
подключения проверена во всех одиннадцати.

| переменная | литерал в `<style>` страницы | **вычисленное значение** | откуда |
|---|---|---|---|
| `--black` | `#0a0a0a` | `#f2f1ec` | `site-skin.css:12` → `--ds-bg` |
| `--white` | `#f5f5f4` | `#0a0a0a` | `site-skin.css:16` → `--ds-text` |
| `--red` | `#fe2c1f` | `#ff6422` | `site-skin.css:11` → `--ds-accent` |
| `--gray` | `#888` | `#5f5f59` | `site-skin.css:17` → `--ds-text-secondary` |

`public/site-skin.css` подключается в HTML-е **после** инлайн-`<style>`
страницы (проверено по номерам строк во всех одиннадцати: `content-day.html`
15→53, `reels.html` 32→80, `event-video.html` 32→80, `reklamnye-roliki.html`
32→82, `photo.html` 33→144, четыре статьи — тем же порядком). Специфичность у
обоих `:root` одинаковая, поэтому выигрывает поздний.

Вычисленные стили корпуса `/reels`:

| элемент | фон | текст | скругление |
|---|---|---|---|
| `body` | `rgb(242,241,236)` = PAPER | `rgb(10,10,10)` = INK | 0 |
| `nav a` | прозрачный | `rgb(95,95,89)` | 0 |
| `.cta` | `rgb(255,100,34)` = SIGNAL ORANGE | `rgb(16,16,16)` | **3px** (не 4px из страницы) |
| `.price-card` | прозрачный | `rgb(17,17,17)` | **0** (не 4px из страницы) |
| `.card p` | прозрачный | `rgb(89,89,83)` | 0 |
| `footer` | `rgb(8,8,8)` | `rgb(244,244,239)` | 0 |

`/photo` даёт ту же картину (`--black: #f2f1ec`, `.price-card` radius 0,
`.card p` `#595953`).

**Что это значит для фазы 5.** Инвентаризация в §5.1 предполагала это по
каскаду — теперь это измерено. Корпус девяти страниц уже сидит на токенах,
поэтому `data-theme="dark"` перекрасит их **сам**, без правок в `<style>`
страниц: локальные hex и `rgba(255,255,255,α)` в этих блоках — мёртвый код,
как и локальные `border-radius`, которые перебиваются правилом
`site-skin.css:119`. То есть оценка «средне» для шести услуг и четырёх статей
из §1 инвентаризации завышена: по корпусу это «метка почти без правок».

**Но** ровно так же измерено, что метка обнажает слой `!important`
`site-skin.css` — см. §3. Поэтому порядок для статики: сначала снять слой,
потом метку.

|---|---|---|---|
| `/ceny` | `rgb(242,241,236)` | **`none`** | `tokens.css`, бандл `design-system-*`, бандл `index-*` |
| `/cvetokorrekciya` | `rgb(242,241,236)` | **`none`** | бандл `design-system-*`, бандл `index-*` |

`src/index.css:82-84` (`radial-gradient(..., rgba(254,44,31,0.06), ...)`)
загружается — таблица `index-*` в списке стилей есть — но проигрывает
`src/design-system.css:127` (`body { background: var(--ds-bg) }`), которое идёт
позже при равной специфичности. Вывод инвентаризации подтверждён: свечения в
рендере нет.

Практический вывод: править `index.css:82` ради тёмной темы не нужно. Но
оставлять правило, которое всегда перебивают, — это будущая ошибка для того, кто
поменяет порядок импортов; чистить в задаче про мёртвый CSS (§6.4 инвентаризации).

Побочно замерено на этих же страницах: `.price-page-hero p` и `.ds-eyebrow`
дают `rgb(200,50,39)` = `#c83227` — легаси-красный из `--ds-accent-text-legacy`.
Это задокументированное решение («мелкий акцентный текст на светлом остаётся до
перевода страницы на тёмное», `SITE-HANDOFF.md:208-210`), не дефект.

## 3. Ответ на вопрос (б) и главная находка: пилот и калькулятор

### 3.1 `/video-dlya-marketpleysov` — страница «уже переведена», но с 7 провалами контраста

Контрольный замер механизма: `data-theme="dark"` есть, `theme-color` =
`#0A0A0A`, `color-scheme: dark`, `--ds-bg` = `#0a0a0a`, корпус
`rgb(10,10,10)` / текст `rgb(242,241,236)`. Механизм работает.

Но полный скан текста по элементно даёт **7 уникальных пар ниже порога**:

| `p` 11px («Съёмка и монтаж…») | `rgba(10,10,10,.62)` | `rgb(10,10,10)` | **1.00** | 4.5 |

| ссылка шапки «Главная» | `rgb(217,215,209)` | `rgb(241,240,234)` | **1.26** | 4.5 |
| `h3` («Видео для карточки») | `rgb(17,17,17)` | `rgb(39,39,39)` | **1.26** | 3.0 |
| `.card-num` («01») | `rgb(89,89,83)` | `rgb(39,39,39)` | **2.12** | 4.5 |

Виновники — литералы в слое `!important` `public/site-skin.css`, которые
писались под светлые страницы и не переворачиваются токеном:
`:884 section { color:#111 !important }`, `:129`/`:135 .card p { #595953 }`,
`:939`, `:1005 .platform`, `:1605`-подобные правила шапки.

Это подтверждает §6.2 инвентаризации («пилот не такой уж чистый») уже не как
оценку по строкам, а как измеренный дефект: **прежде чем вешать метку на
остальные десять статических страниц, надо снять `!important`-слой**, иначе
каждая из них получит те же семь пар.

### 3.2 `/calculator` — 36 невидимых ссылок в подвале

`/calculator` — React-корень, поэтому `site-shell.js` к нему не подключается
(`vite.config.ts:91`) и `body.site-static` не появляется (замер: `bodyClass:
""`). Следствие: фон корпуса берётся не из токена, а из литерала
`site-skin.css:1032 body { background:#f7f7f5 !important }` — замер
`rgb(247,247,245)`, тогда как `--ds-bg` = `#f2f1ec`. **Фон калькулятора вообще
не управляется темой**: метка `data-theme="dark"` его не перекрасит.

Скан по элементно: **37 узлов ниже порога**, из них 36 — один и тот же случай:

```
footer.calc-footer · цвет rgba(255,255,255,0.7) на rgb(247,247,245) · контраст 1.07
«Рекламные ролики», «Видеосъёмка мероприятий», «Reels для бизнеса»,
«Портфолио», «Операторская работа», «Концерты» … — вся карта сайта в подвале
```

Причина в исходнике: `calculator.html:62`
`.calc-footer nav a { color: rgba(255,255,255,0.7); }` — белый литерал, а фон
подвала `calculator.html:59` не задаёт цвета вовсе, так что ссылки лежат на
светлом корпусе. Собственный `:root` страницы с `--black: #0a0a0a`
(`calculator.html:16-26`, включая локальный `color-scheme: dark`) перебит
`site-skin.css` — корпус стал светлым, а литерал в строке 62 остался белым.

Ещё один узел: `div.calc-hint` — `rgb(255,100,34)` на белом, контраст 2.93
(оранжевый SIGNAL на белом — известный предел бренда, но для 13px текста мало).

## 4. Мобильная ширина: жалобы владельца воспроизводятся

Замер на 598px (см. оговорку в §0 про 390).

### 4.1 `/portfolio/events` — блок фильтров уходит за левый край

```
nav.v3-filters.v3-shell   left = -4px   right = 191px   width = 195px
пункты: «ВСЕ» left=1 · «СЪЁМКА» left=56 · «ПОСТ» left=129
горизонтального скролла страницы нет: scrollWidth 598 == clientWidth 598
```

Виновник — `src/design-system.css:828` внутри `@media (max-width: 767px)`:

```css
.v3-filters { top: 66px; margin-inline: -4px; }
```

Отрицательный `margin-inline` наложен на элемент, который уже ограничен
`.v3-shell { width: min(calc(100% - clamp(24px,4vw,64px)), …) }`
(`design-system.css:600`) — то есть отступ съеден дважды, и левый край уезжает
за ноль. Правее того же правила, в `design-system.css:1493`, для
`.v3-catalog .v3-filters` задан `max-width: calc(100% - 24px)`, который
компенсирует это на десктопе, но не отменяет `margin-inline: -4px`.

Заодно тем же сканом поймано: `div.yel-cookie__box` (`left=-5`, `right=603`) —
баннер cookie шире вьюпорта на 5px с каждой стороны. Это `public/cookie-consent.js`,
к теме отношения не имеет, но к «вылезает за экран» относится.

### 4.2 Открытое мобильное меню: «Услуги» и «Портфолио» — белый по светлому

После клика по `.v3-nav__menu` (`body` получает класс `v3-menu-open`) полный
скан даёт **ровно два** узла ниже порога — и это именно те два пункта, о
которых говорил владелец:

```
summary «Услуги»    цвет rgb(255,255,255)  фон rgb(239,239,234)  контраст 1.15
summary «Портфолио» цвет rgb(255,255,255)  фон rgb(239,239,234)  контраст 1.15
```

Механизм найден по исходнику, и он точечный:

- `design-system.css:622` задаёт меню тёмным и светлым текстом:
  `.v3-mobile-menu { background: rgba(11,11,11,.97); color: #fff }`;
- `design-system.css:1383` (внутри `@media (max-width: 900px)`) переворачивает
  меню на светлое: `background: rgba(244,244,239,.98)`, а текст чинит
  **только ссылкам** — `:1384 .v3-mobile-menu a { color: #090909 }`;
- «Услуги» и «Портфолио» — не ссылки, а `<summary>` из
  `.nav-dropdown-mobile-group` (`design-system.css:1689`), и правило `:1384` их
  не касается. Они наследуют белый из `:622` → белый на белом.

Пункты выпадашек после раскрытия видны, потому что они `<a>` — отсюда и
впечатление «пока не нажмёшь».

## :hover и :focus-visible

> ⚠️ Раздел переписан после пересъёмки (см. «Поправка к методике» ниже).
> Первая версия этого раздела утверждала, что наведение не меняет цвет на 112
> записях из 135, — это была мера середины CSS-перехода, а не состояние сайта.

- Случаев, где наведение или фокус **роняет** контраст ниже 4.5 — **ноль**
  (в переснятом кадре тоже ноль: ни одна пара «цвет/фон» в состояниях не
  уходит ниже порога сама по себе; единственные записи ниже 4.5 перечислены в
  пункте про пилот — они ниже и в обычном состоянии тоже).
- Записей `focus` без `outline: none` и без изменения цвета — ноль: там, где
  `:focus-visible` сработал, индикатор есть.
- **Наведение меняет цвет на 121 записи из 140** — то есть отклик на `:hover`
  в сайте есть почти везде; вывод прежней версии («не меняет ни цвет, ни фон,
  ни прозрачность») был артефактом замера до завершения перехода `color .18s`.
- 153 записи помечены `focus (не visible)`: программный `element.focus()` не
  всегда попадает в `:focus-visible` — это ограничение метода, а не свойство
  сайта.
- Единственный маршрут с контрастом состояний ниже 4.5 — `/video-dlya-marketpleysov`
  (пилот): `ссылка футера` = `rgb(244,244,239)` на SIGNAL ORANGE
  `rgb(255,100,34)` = **2.68** во всех трёх состояниях. Причина разобрана в
  «Поправке к методике», пункт 2.

## Поправка к методике (пересъёмка того же кода)

1. **«load» ≠ «страница в покое».** Первый полный прогон А1 мерил сразу после
   события `load`; на `/content-day` в этот момент играёт 33 анимации, и
   `getComputedStyle` отдаёт **стартовое** значение перехода. Из-за этого
   сверка ночных коммитов «до/после» показала расхождение цвета ссылок шапки
   на `/content-day` и `/event-video`, которого правки не вызывали: A/B-опыт
   (вернул удалённый в Б3 `:root` в `dist/` строка в строку) дал тот же цвет —
   то есть дельта была в тайминге замера. Исправлено в `f6f2370`: ожидание
   покоя анимаций (бесконечные и scroll-driven не ждём), увод курсора перед
   меркой «обычное», опция `--only`.
   Пересъёмка всех 140 замеров того же кода: **0 расхождений** по probe-
   свойствам и по `scrollWidth` — весь раздел А1 про «обычное» состояние,
   геометрию и переполнение остаётся в силе; поменялись только `:hover` /
   `:focus-visible`.
2. **Кнопки брендбука на пилоте теряют цвет из-за каскада, а не из-за токенов.**
   `public/site-skin.css:44` — `.site-static a { color: inherit }`,
   специфичность (0,1,1); `public/bb-components.css:38` — `.bb-btn { color:
   var(--ds-on-accent) }`, специфичность (0,1,0). Skin подключён после
   компонентов, поэтому выигрывает он, и подпись на оранжевой заливке
   наследуется от корпуса. Замерено на `/video-dlya-marketpleysov`:
   `PAPER на ORANGE = 2.62` (навигация и hero-CTA), `#f4f4ef на ORANGE = 2.68`
   (футер), тогда как `INK на ORANGE = 6.43` — то, что требует брендбук
   («белый текст на оранжевом — никогда»). `/_kit` те же компоненты рендерит
   правильно (`rgb(16,16,16)` на оранжевом), потому что грузит `tokens.css` +
   `bb-components.css` **без** `site-skin.css`. Затронуты ровно две страницы —
   единственные, где есть классы `bb-*`. Правка в одну строку предложена в
   `docs/audit/night-log.md`, «Решить владельцу» п.8; сам я её не вношу — это
   вне очереди смены и меняет вид пилота.
3. **Шум, который искать бесполезно:** `div.v3-marquee__track` на `/` @390
   снялся в разных кадрах бесконечной анимации (left −1 против −29). Это
   смещение бегущей строки между запусками, а не регрессия; сравнение снимков
   надо читать с этой оговоркой.
