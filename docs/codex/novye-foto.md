# Как добавить новые фотографии

Проверено по коду20.10.2026. Инструкция для будущих реальных кадров: сами фотографии этим заданием не добавлялись. Все действия выполняются в рабочей копии сайта, исходники — в её игнорируемой папке `_agent-reports/photo-incoming/`. В старые внешние архивы по путям из карты не переходить.

## Исходник и реестр

1. Получить реальные отобранные кадры и подтверждённое разрешение на публикацию. Название серии, роль Юрия, дата и имена — только из подтверждённых данных. Alt описывает видимое в кадре. Изображения и подписи не генерировать вместо съёмки.
2. Положить оригиналы в `_agent-reports/photo-incoming/<серия>/`. Они не коммитятся и не попадают в dist. Проверить, что папка действительно исключена Git.
3. В `scripts/photo-map.ts` добавить явные записи `SINGLE_PHOTOS`: уникальный ASCII id и путь относительно корня `--source`. Например, `series-new-01` — лишь технический пример id, не вымышленный кейс. Не менять порядок старых кадров. Для новых путей не использовать `../`, выходящий из разрешённой папки.
4. Для кадра основной галереи `/photo` проверить `PORTFOLIO_GALLERY_IDS`: набор получается из `SINGLE_PHOTOS`, списка `PORTFOLIO_PHOTO_PREFIXES` и исключений. Новый префикс сам туда не попадёт. Расширение списка — осознанный выбор публикуемой серии, а не автоматическое добавление всех исходников. Репортаж отдельного блока не нужно автоматически превращать в портретную галерею.

## Генерация размеров

Из корня рабочей копии, после регистрации настоящих id, заменить пример префикса на выбранный:

```sh
TMPDIR=/tmp/yl41 node_modules/.bin/tsx scripts/process-portfolio-photos.ts --source "$PWD/_agent-reports/photo-incoming" --only series-new
```

`--only` выбирает точный id или id, начинающийся с `<prefix>-`. Он сливает результат с существующим `src/lib/portfolio-photos.manifest.json`. Без `--only` скрипт обрабатывает всю карту и переписывает манифест: такой запуск требует полного исходного архива, включая исторические соседние папки, и сейчас не разрешён.

Скрипт `scripts/process-portfolio-photos.ts` использует существующий sharp: поворот по EXIF, WebP quality82, ширины480/960/1600 без увеличения исходника. Если оригинал меньше480, остаётся его доступная ширина. Канонический `<id>.webp` — самый большой из обычных доступных размеров; меньшие получают суффикс `-480w`/`-960w`. Для id из `PORTFOLIO_GALLERY_IDS` при достаточной ширине создаётся ещё `<id>-2400w.webp`. Действительные width/height/widths записываются в манифест. Метаданные EXIF не сохраняются; для HEIC на macOS используется системный sips с временным PNG. TMPDIR должен оставаться разрешённой временной папкой.

Результат: `public/portfolio-photos/` и манифест. Генерация фотографий — отдельная команда; `npm run build` не обрабатывает новые оригиналы автоматически. Проверить diff: появились только нужные id, старые записи и фотографии не пропали.

## Как кадр появляется на странице

`photo.html` содержит явную разметку кадров. Запись в карте и манифесте сама по себе не добавляет кнопку в галерею.

Добавить реальный кадр в подходящий существующий блок: канонический `src`, только существующие варианты `srcset`, `sizes` под занимаемую колонку, реальные width/height и конкретный alt. Учитывать ориентацию и сохранённый замысел сетки; первый экран и нижнюю галерею проверять отдельно. Изображения ниже экрана — lazy. Высокий приоритет нужен только реальному LCP-кадру, не всей серии.

Лайтбокс собирает кнопки по `data-group` и `data-index`. Индексы внутри группы должны оставаться последовательными в порядке кадров; проверить первый/последний, стрелки, Escape, возврат фокуса и соотношение сторон. Существующие опубликованные кадры не переставлять без отдельной задачи. Видимый счётчик и описание серии в `photo.html` должны соответствовать фактической подборке. Новое название или факт не выводятся из имени файла автоматически.

Для React-страницы использовать существующий `PortfolioImage` и зарегистрированный id, чтобы размеры и srcset брались из манифеста; не создавать второй реестр размеров вручную. Новые маршруты потребуют ROUTE_MANIFEST, prerender, sitemap и один H1; для добавления кадра на существующую страницу новый маршрут не нужен.

## OG-превью

Единственное соответствие «маршрут → опубликованный кадр» — `src/public/ogImages.data.ts`. После добавления настоящего кадра в публичную страницу можно указать его публичный путь для нужного маршрута. Превью не должно изображать несуществующую работу или использовать запрещённые кадры.

`scripts/ogImages.ts` вызывается при сборке/prerender: rotate, центральный crop1200×630, JPEG quality82 в `dist/og/`; метатеги получают абсолютный URL и размеры. Исходник читается из `public/`, не из приватной папки оригиналов. `dist` вручную не редактировать; общий OG-кэш мессенджера не доказывает, что новый файл не опубликован.

## Проверка и выпуск

Сначала просмотреть полученные файлы и страницу локально на390/1440: кропы, ориентация, резкость, подписи, сетка, лайтбокс. Проверить размеры фактически сгенерированных файлов, а не только названия srcset.

```sh
TMPDIR=/tmp/yl41 npm_config_cache="$PWD/_agent-reports/npm-cache" npm run check
```

Полный check включает проверки медиа, `photo-aspect-ratio`, `portfolio-image`, атрибутов width/height/alt, OG1200×630, SEO и геометрии. Не переписывать эталон без просмотра и объяснения намеренной правки; не ослаблять проверки. Коммитить производные публичные файлы, карту, манифест, разметку и документацию; оригиналы и отчёты не коммитить. Отдельная ветка/PR, зелёный CI, выпуск только разрешённым путём и живые GET/H1/мобильная проверка после него.
