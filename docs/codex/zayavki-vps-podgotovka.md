# Заявки на VPS: SMTP и журнал — draft, не включать

Обновлено 20.10.2026 по PROMPT-48. PR #28 остаётся draft. Фабрика `server/lead-delivery-app.js` не импортируется production-server, API router или PM2, не запускает слушатель и не меняет nginx. Выпуск остальных PR не включает этот обработчик.

Основной подготовленный канал — прямой SMTP Яндекса, `smtp.yandex.ru:465`, с проверкой сертификата и имени сервера. На VPS три попытки установили TCP/TLS к Яндексу465/587 и Mail.ru465; VK443 вернул HTTP404 после TLS. Письма, авторизация SMTP и VK messages.send не проверялись. Vercel/Telegram с VPS недоступны в измеренной серии. Прокси, VPN и туннели не используются.

## Как обрабатывается заявка

Выключено до `LEAD_VPS_ENABLED=true`. Основной режим `LEAD_DELIVERY_CHANNEL=smtp-yandex` требует почтовые настройки, абсолютный путь закрытого журнала и существующие серверные настройки БД. Relay и Telegram в этом режиме должны быть выключены. Без предпосылок приложение возвращает503.

Сохраняются настоящие CSRF и cookie, действующие версии согласия/политики, список форм, проверка контакта, honeypot, лимит5 заявок за10 минут, ограничение JSON32КБ и Origin. После валидации полная заявка и сведения о согласии записываются в локальный файл0600 внутри каталога0700; файл и каталог синхронизируются на диск. Только затем вызывается существующая атомарная RPC `record_lead_with_consent`, затем SMTP. Идентификатор БД связывается с локальным журналом событий.

При ошибке диска нет успешного приёма и нет отправки. При ошибке БД заявка остаётся в локальном журнале, но ответ503 и письмо не отправляется. При ошибке SMTP возвращается202 с `queued:true`: это подтверждение устойчивого сохранения, а не доставки письма. Запись остаётся с событием `mail_failed`. При успехе SMTP —200 и `mail_sent`. Уведомление Telegram в SMTP-режиме не вызывается. Старый Telegram-адаптер доступен только при явных `LEAD_DELIVERY_CHANNEL=legacy` и `LEAD_TELEGRAM_ENABLED=true`; сейчас его не включать.

Пароль SMTP передаётся curl через pipe конфигурации, письмо — через отдельный pipe; пароль не попадает в argv, временный файл или журналы. Используется установленный curl, зависимостей npm не добавлено. Посетительский текст кодируется MIME/base64, не становится SMTP-командой или заголовком. Ограничение одного соединения30с и внешнего процесса35с; ослабления TLS нет.

## Что владелец делает руками перед отдельным разрешением

1. В настройках Яндекс Почты разрешить почтовые программы и пароли приложений, затем создать отдельный пароль приложения типа «Почта» для заявок. [Инструкция Яндекса](https://www.yandex.ru/support/yandex-360/business/mail/ru/mail-clients/others). Для личного ящика также [официальная инструкция](https://www.yandex.com/support/yandex-360/customers/mail/en/mail-clients/others).
2. Самостоятельно вписать в закрытый серверный `.env`: `LEAD_SMTP_USER` (полный адрес отправителя), `LEAD_SMTP_PASSWORD` (пароль приложения), `LEAD_MAIL_TO` (свой адрес получения). Существующие `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` остаются серверными. Секреты не передавать в чат, PR, аргументы shell или логи; Codex пароль не видит и не вводит.
3. Подготовить каталог, например `/var/lib/yelyginn-leads`, вне public/dist и web-root, с правами0700 и доступом только серверному процессу; указать `LEAD_JOURNAL_DIR`. Согласовать срок хранения, резервное копирование, контроль свободного места и удаление заявок после срока. Файлы содержат персональные данные. Шифрование на диске и бэкапы этот draft не настраивает.
4. Проверить доступность существующей БД и RPC в изолированной среде, права каталога, curl с TLS и почтовые настройки. Наличие переменных и GET configured ещё не доказывают доставку.
5. Отдельно сказать «да» на выпуск обработчика. До этого `LEAD_VPS_ENABLED` остаётся выключенным, PR #28 не мержится и не выкладывается. Подключение отдельного процесса только к loopback, переключение nginx, резервная копия, `nginx -t`, reload и откат потребуют отдельного подготовленного выпуска. Сейчас эти изменения не сделаны.
6. После разрешённого выпуска — один согласованный тест: сверить запись согласия в БД, локальный журнал и фактическое письмо во входящих/спаме. Не считать успешный GET подтверждением доставки.

## Восстановление после сбоя и пределы draft

Автоматического worker повторной отправки пока нет. Записи `mail_failed` и записи без `mail_sent` требуют контролируемого восстановления: сначала проверить входящие и журнал БД, затем отправить уведомление по локальному идентификатору и записать результат. После обрыва в момент принятия письма SMTP возможна неопределённость; обещания exactly-once нет. Автоматически повторять все письма или удалять исходные записи нельзя. Запись с `consent_failed` сначала требует регистрации согласия в БД. Процедура повторов, мониторинг и срок хранения должны быть завершены до подключения production.

Тесты — только loopback и фикстуры: прежние утверждения сохранены, fixture старого режима явно включает legacy/Telegram; новый режим проверяет CSRF, согласие, Origin, валидацию, лимит, ошибку диска/БД/SMTP, сохранность текста, MIME, права и запрет симлинков. Реальные SMTP/Telegram/production POST не выполнялись. Правила SMTP: [RFC5321](https://datatracker.ietf.org/doc/html/rfc5321/).
