# Прямая доставка заявки на VPS — подготовка, не включать

PROMPT-47 А.5, 20.10.2026. Модуль `server/lead-delivery-app.js` нигде не подключён. Нельзя включать его при выпуске интерфейсного исправления или остальных PR.

Выбран отдельный Express app с двумя существующими обработчиками: GET `/api/csrf` и `/api/send-form`. Сохраняются CSRF, актуальные версии согласий, валидация, лимиты, атомарная регистрация заявки и согласия в БД, проверка ответа Telegram. Нет второго механизма, обходящего consent journal. Почтовой доставки и дискового журнала в этом варианте нет.

Перед включением владелец сам размещает на сервере действующие `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`; затем явно разрешает `LEAD_VPS_ENABLED=true`. Значения не передавать через чат, командную строку, PR или журналы. `LEAD_RELAY_ENABLED` должен быть выключен, иначе приложение вернёт503. Без любого обязательного параметра возвращается503, обработчик не вызывается. GET configured — наличие переменных, не проверка соединения с БД или доставки.

Отдельное подключение должно слушать только `127.0.0.1:3010`, использовать штатный менеджер процесса и HTTPS через существующий nginx. Импорт фабрики сам не запускает слушатель. Новые конфиги PM2/nginx и правка production-server.js не подготовлены к автоматическому применению. Миграция маршрута требует отдельного разрешения: условное разрешение47 А.6 исправить доказанную ошибку существующего location не означает разрешения перенести backend.

Обязательные условия до подключения: исходящий HTTPS к Telegram работает, БД доступна и RPC `record_lead_with_consent` успешно проверена в изолированной среде, политика хранения соблюдена. В диагностике20.10 Telegram с VPS таймаутит — перенос сам по себе проблему не исправляет. Не запускать реальные POST ради проверки. Одну внешнюю тестовую заявку47 можно использовать только после исправления; учитывать общий лимит одной за смену.

Порядок будущего выпуска: проверка этих условий → отдельное согласование подключения → резервная копия конкретного location → локальный GET и негативные проверки CSRF/согласия → переключение endpoint → nginx -t → reload → GET главной и формы → разрешённый тест → контроль записи и доставки. При регрессе вернуть location из копии и reload. Это план, сейчас команды на сервере не выполнялись.

Тесты адаптера используют только loopback и фикстуры: выключено по умолчанию, отсутствие секрета/БД, запрет relay, реальный CSRF и согласие, запрет чужого Origin, неверный JSON, сохранение502. Никаких Telegram или production POST. Существующие интеграционные тесты продолжают проверять обработчик.

Дальше можно рассмотреть защищённый outbox с повторной доставкой. Для него отдельно нужны шифрование, ключ, лимиты места, срок хранения, процедура восстановления и защита от повторной отправки; этот модуль не обещает устойчивой очереди и не сообщает об успешном приёме при недоступной БД.
